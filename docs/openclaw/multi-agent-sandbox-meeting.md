# 🎯 OpenClaw 多Agent三方沙盘会 — 使用操作与流程文档

> 用 3 个独立人格的 AI Agent 模拟策划评审中的 PM、程序、QA 三方视角，在正式开发前完成一轮高质量的需求沙盘推演。

---

## 一、概述

### 1.1 什么是多Agent三方沙盘会？

多Agent三方沙盘会是基于 [OpenClaw](https://github.com/nicepkg/openclaw) 多 Agent 框架搭建的 **AI 驱动需求评审系统**。它通过 3 个拥有独立记忆、独立人格、独立知识库的 AI Agent，分别扮演 **PM（产品经理）**、**Programmer（程序员）**、**QA（测试工程师）** 三个角色，在正式三方会之前先对需求文档进行多轮碰撞讨论，输出一份结构化的分析报告。

### 1.2 解决什么问题？

在软件开发流程中，**三方会**（PM + 程序 + QA 的需求评审会）是需求落地前最关键的环节。但传统三方会常见以下痛点：

| 痛点 | 描述 |
|------|------|
| **准备不足** | 参会人拿到需求文档后没时间细看，会上现场读文档，讨论流于表面 |
| **视角遗漏** | 程序只关注"能不能做"，QA 只关注"怎么测"，PM 只关注"需求全不全"，缺乏交叉碰撞 |
| **结论模糊** | "到底哪些是硬阻塞""哪些可以后续补"没有明确分级，开发启动后反复对齐 |
| **经验依赖** | 评审质量高度依赖参会人经验，新人或跨模块评审时容易漏掉关键风险 |

### 1.3 核心价值

- 🚀 **降低评审门槛**：即使没有经验丰富的技术负责人在场，AI 也能提供系统化的视角覆盖
- 📋 **强制结构化输出**：协议保证每轮讨论都有明确的输入和输出格式，不会开成"闲聊会"
- ⚠️ **前置风险暴露**：在正式开发前就发现规格漏洞、技术风险和测试盲区
- 📖 **可复现的讨论过程**：每次沙盘会的完整对话记录都是项目知识资产

> **注意**：这不是要取代真人三方会，而是 **让 AI 先帮你把需求"吵"一遍**，让真人三方会的讨论起点更高。

## 二、系统架构

### 2.1 系统组成

整个系统基于 OpenClaw 多 Agent 框架搭建，包含以下核心组件：

- **主控 Agent（星期五）**：会议主持人，负责流程编排
- **PM Agent（需求局长）**：产品经理视角
- **Programmer Agent（奇码博士）**：高级程序员视角
- **QA Agent（蛛网质检侠）**：测试工程师视角
- **IM 群组**：人类可见的输出面板
- **A2A 通信通道**：Agent 间的消息通道（sessions_send）

### 2.2 四个 Agent 的角色定位

| Agent | 名称 | 角色 | 核心职责 |
|-------|------|------|----------|
| Main | 星期五 🎯 | 会议主持人 | 发起会议、推进轮次、Sync Gate、汇总结论 |
| PM | 需求局长 📋 | 产品经理 | 代表策划意图，评估用户体验，守护需求完整性 |
| Programmer | 奇码博士 🔧 | 高级程序员 | 评估技术可行性、工作量、风险，给出实现方案 |
| QA | 蛛网质检侠 🕸️ | 测试工程师 | 找边界case、挑战技术方案、定义验收标准 |

> **关键设计原则**：主控（星期五）**不参与**业务讨论，只负责流程编排。它是会议的"主持人"，不是"参会者"。

### 2.3 独立 Workspace 与记忆系统

每个 Agent 拥有完全独立的 workspace 目录：

```
agents/
├── pm/
│   ├── SOUL.md        ← 行为规范（怎么做）
│   ├── IDENTITY.md    ← 角色认知（我是谁）
│   ├── MEMORY.md      ← 长期记忆（历次会议经验）
│   ├── AGENTS.md      ← 协作规则
│   └── memory/        ← 日常记忆文件
├── programmer/
│   ├── SOUL.md / IDENTITY.md / MEMORY.md ...
│   └── memory/
└── qa/
    ├── SOUL.md / IDENTITY.md / MEMORY.md ...
    └── memory/
```

**信息隔离的意义**：

- **PM 不知道 Programmer 的技术细节**，反之亦然——信息隔离让每个 Agent 必须从自己的专业视角出发
- **每个 Agent 有独立的长期记忆**，可以积累历次评审的经验教训
- **知识库通过 Skill 系统注入**，而不是硬编码在 prompt 中

## 三、通信机制

### 3.1 sessions_send：Agent 间的消息通道

Agent 之间通过 OpenClaw 提供的 `sessions_send` 进行 **A2A（Agent-to-Agent）通信**。每个 Agent 有一个唯一的 session key：

```
Main:       agent:main:sessions
PM:         agent:pm:sessions
Programmer: agent:programmer:sessions
QA:         agent:qa:sessions
```

**通信示例**：主控向 PM 发送 Round 1 任务：

```
sessions_send(
  sessionKey = "agent:pm:sessions",
  message    = "议题：[需求文档内容]\n请从 PM 视角给出意见。完成后在 IM 群组发言。",
  timeoutSeconds = 0  // fire-and-forget，不等回复
)
```

> ⚡ **`timeoutSeconds=0` 是关键设计**——fan-out 阶段不等待任何 Agent 回复，三方并行处理，避免串行阻塞。

### 3.2 IM 群组：人类可见的输出面板

每个 Agent 绑定一个独立的 IM 机器人账号，发言时各自以自己的身份出现在群里：

```
// PM 在 IM 群组发言
message(
  action    = "send",
  channel   = "im",
  accountId = "pm",       // 绑定到"需求局长"这个 Bot
  target    = "group_xxx",// IM 群组 ID
  message   = "📋 需求局长：\n【Round 1 — PM独立评审】..."
)
```

人类在 IM 群组里看到的就是 **3 个不同身份的机器人在独立发言**，体验上就像 3 个真人在讨论。

### 3.3 Sync Gate：同步关卡

每轮结束后，各 Agent 通过 A2A 向主控报告完成状态：

```
PM         → agent:main:sessions: "[Round 1 完成] PM 已在 IM 群组发言。"
Programmer → agent:main:sessions: "[Round 1 完成] Programmer 已在 IM 群组发言。"
QA         → agent:main:sessions: "[Round 1 完成] QA 已在 IM 群组发言。"
```

- 主控收到 **3 个 `[Round 1 完成]` 信号**后，自动推进到 Round 2
- 如果 **90 秒内未收齐**，则带已有结果继续推进——**永远不会无限等待**

## 四、三轮对话协议（核心流程）

这是整个沙盘会最核心的设计。三轮对话模拟了真实三方会中 **"独立思考 → 交叉碰撞 → 收敛共识"** 的过程。

### 4.1 Round 1：独立判断（Independent Views）

**目标**：三方各自独立审视需求，不受其他角色影响，给出第一视角的判断。

| 角色 | 输出要求 |
|------|----------|
| PM | 重述议题确认理解 → 1-3 个产品角度关切 → 明确表态（支持/反对/有条件） |
| Programmer | 可行性判定（✅可做/⚠️有条件/❌不推荐）→ 需求拆解&工作量 → Top3 风险 |
| QA | 3-5 个关键测试场景 → 边界 case → 质量门禁判定 |

> **为什么要"独立"**：如果 QA 先看到 Programmer 的"可做"判定，可能会减少质疑力度。独立评审确保每个视角都充分表达。

### 4.2 Round 2：交叉回应（Cross-Response）

**目标**：看到其他两方的 Round 1 观点后，进行有针对性的回应——认同、质疑、补充。

主控会把 Round 1 的三方观点摘要发给每个 Agent，要求：

1. **认同**至少一个其他角色的有价值观点（说明是谁的哪个点）
2. **质疑/补充**至少一个点（给出理由）
3. 给出**融合优化建议**

> 🔥 **这是信息密度最高的一轮**——三方在这里真正产生交叉碰撞，而不是各说各的。

### 4.3 Round 3：收敛定稿（Convergence，可选）

**触发条件**：Round 2 仍存在重大分歧或未解决的 trade-off 时才触发。

每个 Agent 必须给出：

- 支持哪个方案（A/B/融合版）
- 什么必须保留 / 什么可以砍
- 上线前置条件

### 4.4 最终总结（主控输出）

主控综合三轮讨论，输出：

- ✅ **总体结论**（可推进 / 需补充 / 不推荐）
- 📋 **三方收敛采纳的方案**
- 🚫 **硬阻塞项清单**
- 🔒 **最低验收前置条件**
- 📝 **下一步行动项**（精确到责任人 + 时间）

## 五、知识库配置

### 5.1 为什么需要知识库？

如果只给 Agent 一个角色 prompt（"你是程序员，评估技术可行性"），它的输出会是通用的、泛泛而谈的。但真实的技术评审需要：

- 知道项目用的是什么引擎、什么语言
- 知道哪些模块有现成框架可以复用
- 知道历史上踩过哪些坑
- 知道工作量估算的基准参考

### 5.2 Skill 知识库内容结构

将项目知识转化为 **Skill**（如 `project-feasibility-review`），包含以下知识模块：

| 模块 | 内容 | 对应评审能力 |
|------|------|-------------|
| 项目架构导航 | 引擎层/游戏层/工具层分层，核心技术栈 | "这个需求改哪一层" |
| 关键目录速查 | 每个功能的目录位置 | "代码在哪里" |
| 现有功能模块索引 | 40+模块的功能→目录→核心文件映射 | "有没有现成可以复用的" |
| 工作量估算框架 | 基准人天参考 + 乘数因子 | "大概需要多少天" |
| 代码搜索策略 | 如何在项目中定位相似实现 | "怎么找类似的代码参考" |
| 风险评估清单 | 性能/一致性/跨服/兼容/安全/可测试 6 维度 | "有什么风险" |
| 隐性经验知识库 | 副本流程图、活动框架复用、排行榜双方案等 | "老手才知道的经验" |

### 5.3 Skill 调用示例

当 Programmer Agent 收到需求评估任务时，会自动加载知识库 Skill，按照 6 步流程进行评估，输出模板如下：

```
💻 奇码博士：
【可行性判定】⚠️ 可做，但有条件
【需求拆解】
  1. 活动主 Manager — gas/lua/ — 1.5 天
  2. 波次刷怪控制 — FlowchartInterface — 1 天
  ...
【现有可复用】FlowchartInterface 波次事件 → 策划可直接配流程图
【工作量估算】共 12 天
【Top 3 风险】
  1. 泥人"成长/分裂/合体"是非标机制...
  2. 3平台并发守怪状态同步...
  3. Boss AI 仇恨表改动回归风险...
【建议】MVP 方案：泥人成长简化为状态切换...
```

### 5.4 三方知识库对比

| Agent | 知识库来源 | 核心内容 |
|-------|-----------|----------|
| PM | SOUL.md 角色设定 | 需求完整性守护、用户体验判断框架、妥协策略 |
| Programmer | Skill（项目知识库） | 项目架构、模块索引、工作量基准、风险清单、隐性经验 |
| QA | SOUL.md + 项目清单 | ConsumeItem 检查、RPC 参数校验、边界 case 思维模式 |

> **Programmer 的知识库是最深的**——因为技术评估需要的项目特定知识最多。PM 和 QA 的知识更多依赖"思维模式"而非"项目细节"。

## 六、使用操作步骤

### 6.1 发起一次沙盘会

**操作方式**：在 IM 群组中 **@星期五**（主控 Agent） 并贴上需求文档内容。

```
@星期五 请评审以下需求：

[粘贴你的需求文档内容]
```

主控（星期五）会自动：
1. 识别需求内容
2. 并行推送 Round 1 任务给 PM、Programmer、QA 三个 Agent
3. 在 IM 群组中发送"会议已发起"的通知

### 6.2 观察 Round 1：三方独立评审

三个 Agent 会在 IM 群组中以各自身份独立发言：

- 📋 **需求局长（PM）**：聚焦产品层面的核心关切——活动目标清晰度、兼容性、用户体验
- 🔧 **奇码博士（Programmer）**：给出技术评估——可行性判定、需求拆解、工作量估算、Top 3 风险
- 🕸️ **蛛网质检侠（QA）**：切入边界 case——列出多维度测试关注点和 P0 级问题

> 用户在此阶段**无需操作**，等待三方完成即可。

### 6.3 观察 Round 2：交叉回应

主控自动收集三方 Round 1 观点并推进 Round 2。每个 Agent 会：

1. **认同**其他角色的有价值观点
2. **质疑/补充**存在问题的点
3. 给出**融合优化建议**

这是信息密度最高的环节——三方真正产生交叉碰撞。

### 6.4 查看最终总结

如果 Round 2 三方已基本收敛（没有重大分歧），主控判断不需要 Round 3，直接输出最终总结。

最终总结包含：

1. **总体结论**：可推进 / 需补充 / 不推荐
2. **硬阻塞项**：开发前必须解决的问题清单
3. **三方收敛方案**：各方妥协后的统一方案
4. **必测 case**：QA 给出的验收测试用例
5. **下一步行动项**：精确到责任人 + 时间

## 七、搭建指南（从零开始）

### Step 1：准备 Agent Workspace

创建以下目录结构：

```
your-workspace/
├── agents/
│   ├── pm/          ← SOUL.md + IDENTITY.md + MEMORY.md
│   ├── programmer/  ← SOUL.md + IDENTITY.md + MEMORY.md
│   └── qa/          ← SOUL.md + IDENTITY.md + MEMORY.md
├── skills/
│   └── your-project-feasibility-review/
│       └── SKILL.md  ← 项目知识库
└── SOUL.md           ← 主控行为规范（会议协议）
```

### Step 2：编写角色 SOUL.md

每个角色的 `SOUL.md` 需要定义：

- **角色定位**：你是谁、核心价值观是什么
- **发言规范**：每轮应该输出什么
- **A2A 通信规则**：完成后如何报告状态
- **多轮会议行为**：Round 1/2/3 各自的模板

### Step 3：构建项目知识库（Skill）

这是差异化最大的部分。针对你的项目，你需要提取：

| 知识类型 | 说明 |
|----------|------|
| 项目架构概览 | 技术栈、目录结构 |
| 现有模块索引 | 功能→代码位置映射 |
| 工作量估算基准 | 基于历史经验的参考值 |
| 风险评估清单 | 项目特有的常见坑 |
| 隐性经验 | 老手才知道的 know-how |

> 💡 **提示**：如果你已经有一篇"项目架构梳理"的文档，那它很可能可以直接转化为 Skill。

### Step 4：配置主控会议协议

在主控的 `SOUL.md` 中定义多轮会议协议，包含：

- **Fan-out 规则**：并行推送、fire-and-forget
- **Sync Gate**：等待信号、超时处理（建议 90 秒）
- **自动推进规则**：收齐信号后必须立刻推进，不等用户确认
- **最终总结模板**

### Step 5：配置 IM 机器人

每个 Agent 绑定一个独立的 IM 机器人，让人类可以在群里看到三方独立发言。

配置要点：
1. 创建 **3 个 IM 自建应用**（PM / Programmer / QA）
2. **统一加入**同一个 IM 群组
3. 在 OpenClaw config 中配置 **channel binding**

## 八、效果对比

### 8.1 一次沙盘会的实际产出

| 产出物 | 内容 |
|--------|------|
| 规格漏洞发现 | 4 个 P0 级问题（真人评审也可能发现，但 AI 更系统） |
| 技术方案 | 状态机简化方案、AI 隔离方案、并发安全方案 |
| 工作量评估 | 12 天分解到子任务级别 |
| 验收标准 | 4 条必测 case + 验收前置条件 |
| 行动项 | 精确到责任人 + 时间的 TODO 清单 |
| 决策记录 | 三方讨论过程和最终结论 |

### 8.2 对比传统三方会

| 维度 | 传统三方会 | AI 沙盘会 |
|------|-----------|-----------|
| 准备时间 | 需要每人提前读文档 | 0，AI 即时处理 |
| 会议时长 | 30-60 分钟 | 15-20 分钟（自动进行） |
| 观点覆盖度 | 取决于参会人经验和状态 | 系统化覆盖，不会遗漏 |
| 输出结构化程度 | 通常是会议纪要（文字记录） | 结构化报告（可直接作为开发输入） |
| 交叉碰撞质量 | 取决于会议氛围和主持人 | 协议保证必须交叉回应 |

## 九、经验教训与最佳实践

### 9.1 踩过的坑

#### 🐛 坑一：主控"出模板等确认"

**问题**：早期版本中，主控在收齐 Round 1 信号后，生成了"模板消息"让用户手动发送，而不是自动推进 Round 2。

**解决**：在会议协议中加入**强制自动推进规则**，明确禁止任何形式的"等用户确认"。

#### 🐛 坑二：信息不隔离导致跟风

**问题**：如果让 Agent 在 Round 1 就能看到其他角色的观点，它们会趋向"和稀泥"而不是独立判断。

**解决**：**Round 1 必须信息隔离**，每个 Agent 只能看到需求文档本身。

#### 🐛 坑三：知识库太泛没用

**问题**：纯角色 prompt 的 Programmer 只会说"这个可以做，大概需要几天"。

**解决**：构建具体项目知识库。有知识库的 Programmer 能说"已有波次事件接口，只需新增 1 个事件接口（0.5-1 天），剩下的策划可以用流程图编排"。**知识库的粒度决定输出质量**。

### 9.2 最佳实践

1. **Round 2 是核心**：经过实践，Round 2 交叉回应是信息密度最高的环节
2. **知识库越具体越好**：项目级知识 > 通用技术知识
3. **超时不能太长**：90 秒是比较好的 Sync Gate 超时时间
4. **主控不参与业务讨论**：保持主持人角色的纯粹性
5. **AI 沙盘会作为预读材料**：将结论作为真人三方会的"预读材料"，提升讨论起点
